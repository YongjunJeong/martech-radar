# UI review constraints

- Sales reviews use desktop web. Prioritize desktop layouts and verification; do not invest in mobile-specific polish or run mobile browser checks unless requested. Existing responsive fallbacks may remain.
- Use the available desktop width with compact spacing. Keep observation dates, counts, limitations, and the recommended action legible; density must not hide decision-critical evidence.
- Statuses describe the next review action, not purchase likelihood. Navigation counts, selected labels, and list membership must agree.
- A company-level contact status must not promote unconfirmed individual tool changes. Collection failures override contact advice.
- `web/static/desktop.css` owns desktop visual overrides. Keep collection logic and schedules independent from presentation changes.
- Desktop typography: body and proposal/email copy 14–15px; dates, evidence counts, labels and help text at least 13px. Use `--text-meta` / `--text-body` for small text. Do not restore 10–12px labels to fit more content. Prefer natural wrapping with readable line height.
- Align common inputs and primary actions to a 40px height. Recommendation checkboxes sit beside their titles; proposal/email headings share a row. Keep category tables' columns consistent and check expanded filters, evidence, custom vendor inputs and notifications at 1024/1280/1440/1920px desktop widths.
- Custom disclosure arrows use `_disclosure_chevron.html`, centred with the label and rotated on the owning `details[open]`. Avoid font-character arrows. Preserve native summary keyboard controls, stable toggle width and reduced-motion support.
- Keep the four review statuses in one horizontal row. Collection administration belongs in the right-hand header menu, separate from company research.
- Company list cards start with aggregate change counts and confirmation readiness. Expand to see every solution's observation summary, ordered by repeated-observation readiness then name. Detailed observation history and direct evidence belong on the company page; the first solution is not a relevance ranking.
- Company detail starts with the contact decision and the same aggregate change summary. Each solution's contact eligibility remains visible while its dates, history, evidence, and questions are collapsed in one disclosure. Collection problems override contact eligibility even when older observations met the repeat threshold.
- Waiting cards and company detail share the next scheduled check and the result being awaited. Dates are read-only projections from the collector's cadence, not contact eligibility deadlines. Show queued/running/overdue states explicitly; for multiple URLs label the earliest page schedule. Aggregate expected results on cards and explain each solution's repeat threshold inside its detail disclosure.
- A solution-type filter selects companies with observed changes in that type. Recompute status counts, contact eligibility, change summaries and waiting guidance from that scope; a repeated change in another type must not promote the selected type. Preserve collection-quality overrides. Carry the type into company detail with a visible scope notice and an explicit return to all types. Filter categories use the same purpose labels as the solution cards.
- Separate capability, solution name, and observation result visually and with HTML whitespace. When releasing CSS changes, bump `css_release` in `base.html` for both stylesheets together so browsers cannot mix old base styles with new desktop styles.
- The observation-tag filter intersects the solution-type filter on the same solution, before status, counts, waiting guidance and contact eligibility are calculated. Carry both filters into detail and back. Baseline/stable tag searches include matching observed solutions even without changes. A new search starts from all review statuses; users can then narrow the status explicitly. Failed collections still override contact eligibility.
- Observation tags use native checkboxes with OR matching; solution type still applies with AND to the same solution. No checked tags means no tag restriction. Preserve repeated `observation` query parameters across status/pagination/detail/back links, accept old single-tag links, and count a company/solution once even when both its direction and fluctuation tags match.
- Solution types also use native checkboxes with OR matching. Apply `(any selected type) AND (any selected tag)` to each solution before company aggregation. Preserve repeated `solution_type` and `observation` values on all navigation links. No selected types means no type restriction; existing single-type links still work. De-duplicate repeated values in both groups.
- Industries use the workspace's industry catalogue (including custom codes), with OR matching at company level. Combine industry membership with the solution/type-tag intersection. Preserve all three repeated parameters on status/pagination/detail/back links; selecting no industries removes only the industry restriction. Recompute all status counts and pagination from the combined scope.
- Keep the filter choices in a native disclosure, collapsed on page load. A persistent selection overview names every selected industry, solution type and observation tag in three labeled groups, wrapping rather than truncating. Name search and reset stay accessible when collapsed. The desktop toolbar uses one compact search row and inline selected-filter groups; no visible submit button is needed with JavaScript. Keep a submit button only in the noscript fallback. Name input automatically refreshes after 350 ms of idle time, deferring Korean IME composition until completion. Checkbox edits update the summary immediately and automatically refresh results after a short debounce; folding alone must not change results. Use the form controls as the only client selection state; server-render the applied summary for JavaScript-free use.
- Keep selection chips outside the disclosure's summary so each X and group clear button is independently accessible. Removal unchecks the underlying controls, preserves the other groups and the open/closed state, and automatically updates results. Hide group clear when empty; move focus to a remaining removal button or the disclosure toggle after deletion. Without JavaScript, show the applied labels and let the native disclosure expose the checkboxes.

## Color direction

Use neutral charcoal / soft white surfaces with teal accents. The direction references WGSN/Coloro's 2026 Transformative Teal and Pinterest's 2026 Jade palette; these are broad design trends, not evidence of SaaS market share. Our hex values are UI adaptations, not official brand swatches. Keep status colors and text labels distinct from brand accents.

## Korean product wording

- Observation tags describe direction separately from contact readiness: 미검출 → 검출, 검출 → 미검출, 다시 검출, 첫 수집에서 확인, 계속 검출. The secondary 검출·미검출 반복 tag requires at least three transitions within the last eight normal, analysis-window/site-scoped observations, matching the evidence history. Do not count it again in direction totals. Failed collections are not absence. Use the same tags on aggregate summaries and solution disclosures; preserve the existing quality and contact rules.

- Use “솔루션 현황” for the vendor navigation and page title. “검출 비율” is the share of monitored companies with usable observations, using their last successful collection; it is not market share or contract share.
- Use “솔루션” consistently in sales views; “정상 수집” for usable collection runs; keep “검출 / 미검출” with the explanation that these are observations, not adoption or termination.
- Label detected accounts “검출된 기업”, not “사용 기업”. Detection scores measure technical evidence, not buying intent.
- Prefer “탐지 기준 / 근거 유형 / 접속 사이트” over “지문 / 증거 층 / 착지”. Preserve dates, quantities, product names and caution about incomplete evidence.

- Automatic filtering fetches the existing GET-rendered result region, replacing counts, cards and pagination as one server snapshot. Keep the form, disclosure state and input focus intact. Invalidate and abort superseded requests immediately; only the latest successful response may update results and URL history. Mark old results busy/inert while waiting or on failure, show an explicit error and retry, and restore controls/results on browser back/forward. Native GET submission remains available without JavaScript.

- Preparation begins with automatic public-company research and KB recommendations. Sales chooses 1–3 read-only scenarios, then generates proposal and email together. Distinguish company evidence from industry hypotheses, show reasons and citations, and offer downloads/copy instead of editing controls.
